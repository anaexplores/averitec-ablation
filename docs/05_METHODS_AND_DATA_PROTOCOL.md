## Принцип провенанса

Все 10 методологических источников проверены 15.11.2026 напрямую:
6 записей разрешены по точному DOI через `api.crossref.org` (HTTP 200, название/авторы/журнал совпадают),
4 записи через `export.arxiv.org` (HTTP 200, полные абстракты сохранены дословно).
Ни один DOI не взят по памяти: кандидат DOI для статьи Макнемара (`10.1007/BF02295985`) при проверке
разрешился в **другую** работу (Brogden 1977) и был отброшен, правильный (`10.1007/BF02295996`)
найден библиографическим поиском. У журнальных записей, полученных через Crossref, абстракты
поставлены как `null` (Crossref не возвращает текст абстракта для этих записей), пересказывать по памяти запрещено.

## 3. Протокол (применяемая часть)

### 3.1 Подготовка данных (каждый датасет)

1. **Снапшот и манифест.** SHA-256 каждого сырого файла, дата выгрузки, класс лицензии, версия датасета, ссылка на карточку (паттерн уже реализован в `data/MANIFEST.json` lost-caveats).
2. **Проверка схемы.** Обязательные поля присутствуют, словарь меток зафиксирован до сплита (например, `supported` / `caveated` / `unsupported`), единицы измерения определены.
3. **Дедупликация на уровне групп.** Кейсы с общим источником/парой склеиваются в одну группу; групповой ключ определяется **до** разбиения.
4. **Журнал чистки.** Каждое решение по данным логируется; после отрисовки сплита по-кейсовые правки запрещены.
5. **Маркировка preexisting vs new** в README репозитория и в отчёте (правило спринта, см. `03_GUIDELINES_AND_RUBRIC.md`).

### 3.2 Правила разбиения

1. **Сплит по группам, а не по строкам:** единицы с общим источником/парой/диалогом не разделяются между сторонами (утечка не-независимости, M06).
2. **Стратификация** по метке и `error_class` внутри каждой стороны.
3. **Один фиксированный сид, записанный в отчёте; сплит рисуется один раз** (M05, M09).
4. **Dev используется только** для фиксации промптов, параметров ретривера и скрипта анализа; **тестовая сторона прогоняется ровно один раз** (M02).
5. **Публичные бенчмарки (MASK, DarkBench) — test-only по определению:** никакой подстройки параметров по ним.
6. **Контаминация и время:** предпочтение дизайнам, устойчивым к утечке (AVeriTeC, ForecastBench как шаблоны, E01/S14).

### 3.3 Статистический план

1. **Пре-регистрация внутри отчёта:** гипотезы, условия, метрики, тесты, критерии остановки пишутся до первого прогона на тесте (M07).
2. **Единица анализа — кейс; условия парные**, значит основной тест — точный **McNemar** для пары «A vs B» по каждому судье отдельно (M01, M02, M04).
3. **Правило бинаризации фиксируется до прогона.** Словарь вердиктов трёхклассный (`supported` / `caveated` / `unsupported`), а McNemar требует бинарный исход: стандартный режим — `alarm = verdict ≠ supported`, строгий режим — `alarm = verdict = caveated`. Оба режима реализованы в `pipeline/score_judges.py` (`--strict`). Анализ McNemar отчёчится в обеих бинаризациях, и обе объявлены в плане анализа заранее.
4. **Пропорции — с 95% интервалами Вилсона**, не вальдовскими (M03); списки промахов и ложных тревог по id уже печатает `pipeline/score_judges.py`.
5. **Мощность / минимально детектируемый эффект считается для фактического размера тестовой стороны** после группового сплита, а не для полного датасета (например, 27 пар при сплите 2/3 dev / 1/3 test дают тестовую сторону ~9 пар, то есть ~18 кейсов); нулевой результат интерпретируется против именно этой, по-датасетной величины (M10).
6. **Семейство сравнений** определяется заранее: обязательное `{A vs B, B vs C}`, опциональное `{A vs D, A vs C}`; поправка по Холму применяется внутри объявленного семейства (M04).
7. **Судьи не смешиваются в один средний**: судейская дисперсия — часть результатов (M08, M09).

### 3.3.1 Условия эксперимента (фиксируются до прогона)

Варьируется **только ретривер-контекст**; модель, промпт-шаблон и подсчёт очков неизменны:

- **A** = только `support_windows` (top-5 BM25, окна по 120 слов);
- **B** = `support + caveat_windows` (preexisting-поведение lost-caveats v0.1.1);
- **C** = `support + caveat-окна из чужого случайного документа` (сохраняются число окон и плотность лимитирующих маркеров, рвётся связь с заявлением);
- **D** (опционально) = только `caveat_windows`.

### 3.4 Правила исполнения эксперимента

1. Один судейский вызов на единицу анализа × условие × судью; промпт-шаблон одинаков по всем условиям. **Поправка 15.11.2026, до любого прогона тест-стороны:** инференс судей идёт через сессии-сабагенты OpenCode, а не через OpenRouter API; утверждения батчируются по 20 на сессию судьи с независимым вердиктом по каждому внутри сессии; батчевость одинакова для всех условий и судей; элементы независимы (разные фактчек-заявления), внутри-батчевое вмешательство оценено как низкое и заявлено здесь. Исходное правило «один вызов API на кейс» сохранено для запасного OpenRouter-раннера. **Вторая поправка 15.11.2026, тоже до любого прогона тест-стороны:** панель из четырёх судей зафиксирована на моделях из пула подписки OpenCode Go, по одной на семейство, вместо ранее намеченных имён пула OpenCode: claude-haiku-5-5 (Anthropic), gemini-4-argon (Google), gpt-6-luna (OpenAI), deepseek-v4-pro (DeepSeek). Те же четыре семейства, что планировались изначально; прежние имена на тест-данных не запускались ни разу.

**Задокументированное отклонение, 15.11.2026, во время тест-прогона:** ячейка test/A/batch00 у судьи DeepSeek (20 из 196 заявлений) не смогла быть получена моделью `opencode-go/deepseek-v4-pro`: три попытки (включая одну с инструкцией не цитировать нецензурную лексику) блокировались контент-фильтром провайдера («Provider blocked the response»). Ячейка получена запасной бесплатной моделью `opencode/deepseek-v4.1-flash-free`, то же семейство DeepSeek, тот же файл промпта, та же инструкция про нецензурную лексику. Все сравнения с участием DeepSeek в условии A показываются в двух вариантах: с этим батчем (смешанная ячейка, помечена) и без него (176 заявлений, одна модель); при расхождении основной считается вариант без батча. Больше ни одна ячейка судья-батч не прогонялась запасной моделью. Для датасетов, где харнесс содержит несколько модельных взаимодействий на единицу (например, belief-эличитации в MASK), единица анализа — пример, вход судьи собирается одинаково по всем условиям.
2. Temperature и остальные параметры сэмплинга зафиксированы и записаны; ретраи и отказы API логируются по кейсам.
3. Проверка цитат (`quote_found_in_source`, уровни L0–L3) прогоняется одинаково для всех условий.
4. В отчёте: что результат устанавливает, чего **не** устанавливает, минимально детектируемый эффект, обязательный аппендикс *Limitations and Dual-Use*.

## 4. Что это даёт относительно рубрики спринта

- **Execution Quality:** парный дизайн, групповые сплиты, заранее зафиксированный анализ, Wilson + McNemar + мощность — это прямое закрытие требований Dimension 2 («тщательная методология с убедительной валидацией», 4 балла).
- **Impact & Innovation:** претензия поднимается с «мы погоняли судей» до «ретривер-контекст — скрытая степень свободы валидности LLM-judge эвалов, и вот её измерение на нескольких датасетах по стандартному протоколу».
- **Presentation:** одна таблица «судьи × условия × датасет» и одна таблица McNemar, остальное в аппендикс.
